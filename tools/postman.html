Postman

P
Kısaca
HTTP istekleri (GET, POST, PUT, DELETE...) atıp cevabı görmeni sağlayan GUI. cURL'ın kullanıcı dostu kuzeni.
↓ İndir ❯ Dokümantasyon

Bu Ne?

Postman'in temel işi: bir endpoint'e elle istek atıp ne döndüğünü görmek. Ama bu kadar değil — gerçek gücü koleksiyon, environment ve test kavramlarında.

  • Collection: API'nin tüm endpoint'lerini gruplayan bir klasör. Takıma share edebilirsin.
  • Environment: {{baseUrl}} gibi değişkenleri "dev / staging / prod" için ayrı ayrı tanımlarsın. Tek tıkla ortam değiştirirsin.
  • Tests: İstek sonrası JavaScript ile assertion yazabilirsin — pm.expect(response.status).to.equal(200). Bu sayede koleksiyon bir "smoke test suite"e dönüşür.
  • Newman: Postman koleksiyonlarını CLI'da çalıştıran araç. Jenkins'e koyup deploy sonrası API'yi otomatik tarayabilirsin.

Tipik Bir İş Akışı

Postman'i koleksiyon + environment ile kullanmak

İçinde Hangi Şıkı Bilmeli?

  • Pre-request scripts: İstekten önce çalışan JS. "Token süresi dolduysa yenile" gibi.
  • Tests: Cevap geldikten sonra çalışan JS. pm.test("status 200", () => pm.response.to.have.status(200));
  • Mock servers: Backend hazır değilken Postman'e fake bir server kurdurabilirsin — frontend devam edebilsin.
  • Runner: Bir koleksiyonu CSV ile besleyip 100 farklı veriyle çalıştırabilirsin.

Diğer Araçlarla İlişkisi

  • Swagger / OpenAPI: Spec'i import et, koleksiyon hazır.
  • Jenkins: Newman ile pipeline'a koleksiyon koş → "API smoke test".
  • Insomnia, Bruno, Hoppscotch: Alternatifler. Bruno açık kaynak ve giderek popüler.
Stajyer notu
Şifre / token gibi sensitive bilgileri direkt request'e değil, environment variable'a koy. Koleksiyonu share ettiğinde şifren leak olmasın.
◆ Gerçek Proje — Student API

Spring Boot + PostgreSQL CRUD

Aşağıdaki örnekler gerçekten çalıştırılan bir projeden alındı. 3 kolonlu öğrenci tablosu: studentNumber, fullName, gpa. Her endpoint için istek, yanıt ve ne öğrendik var.

// Kurulum

PostgreSQL Docker ile ayağa kaldırıldı, Spring Boot otomatik tabloyu oluşturdu (ddl-auto=update). 

# PostgreSQL başlat
docker run --name student-db \
  -e POSTGRES_DB=student_db \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=1234 \
  -p 5432:5432 -d postgres

# Spring Boot başlat
./mvnw spring-boot:run
GET /api/students — tüm öğrencileri listele

Parametresiz, body yok. DB'deki tüm kayıtları array olarak döner. 

// Response — 200 OK
[
  { "id": 3, "studentNumber": "1002", "fullName": "Zeynep Arslan", "gpa": 3.75 },
  { "id": 7, "studentNumber": "1006", "fullName": "Selin Yildiz",  "gpa": 3.20 },
  ...
]
// Test Script
pm.test("Status 200 dönmeli", () => pm.response.to.have.status(200));
pm.test("Response array olmalı", () => pm.expect(pm.response.json()).to.be.an('array'));
pm.test("Response süresi 500ms altında", () => pm.expect(pm.response.responseTime).to.be.below(500));
✓ 3/3 — 114ms — Test Results geçti
POST /api/students — yeni öğrenci ekle

Body'de JSON gönder, DB'ye kaydedilmiş hali (id ile birlikte) döner. 

// Request Body
{
  "studentNumber": "1001",
  "fullName": "Ahmet Yilmaz",
  "gpa": 3.50
}

// Response — 200 OK
{
  "id": 12,
  "studentNumber": "1001",
  "fullName": "Ahmet Yilmaz",
  "gpa": 3.50
}
// Hata Senaryosu — aynı studentNumber tekrar gönderilince
// Response — 409 Conflict
"Bu öğrenci numarası zaten kayıtlı."

İlk deneme 500 döndü — Spring DB constraint hatasını yakalamıyordu. @ExceptionHandler(DataIntegrityViolationException.class) ekleyince 500 → 409'a düştü. 500 = sunucu patladı, 409 = iş kuralı ihlali.

// Test Script
// Duplicate için:
pm.test("Duplicate studentNumber 409 dönmeli", () => pm.expect(pm.response.code).to.equal(409));
pm.test("Hata mesajı doğru", () => pm.expect(pm.response.text()).to.include("zaten kayıtlı"));
PUT /api/students/{id} — öğrenci güncelle

Path'te ID, body'de yeni değerler. Tüm alanı günceller (PATCH değil PUT — fark önemli). 

// PUT /api/students/12
{
  "studentNumber": "1001",
  "fullName": "Ahmet Yilmaz",
  "gpa": 3.80
}

// Response — 200 OK
{
  "id": 12,
  "studentNumber": "1001",
  "fullName": "Ahmet Yilmaz",
  "gpa": 3.80
}
DEL /api/students/{id} — öğrenci sil 
// DELETE /api/students/12

// Response — 200 OK
"12 ID'li öğrenci başarıyla silindi."
// Bu Projede Öğrenilenler
  • pm.test() ile otomatik assertion — her Send'de manuel kontrol yok
  • 500 vs 409 — sunucu hatası ile iş kuralı ihlali aynı şey değil
  • @ExceptionHandler — Spring'de global hata yönetimi
  • Happy path yetmez — aynı veriyi iki kez göndermek, olmayan ID silmek test edilmeli
  • Response time da bir metrik — 500ms sınırı koyunca fark edilir
