Bu Ne?

Jenkins, CI/CD (Continuous Integration / Continuous Delivery) sunucusudur. Tek cümle: "kod değişti → otomatik test edilsin → otomatik paketlensin → otomatik deploy edilsin" zincirini kuran şey. Eskiden tek başına dev'in işiydi: local'de derle, sunucuya FTP ile at, dua et. Jenkins bunu otomasyona bağlar.

Çalışma şekli: Pipeline dediğimiz, çoğunlukla Jenkinsfile adında bir dosyaya yazılan aşamalar (stages) tanımlarsın. Git'e push olunca veya cron tetiklenince Jenkins bu pipeline'ı sırayla yürütür.

Tipik CI/CD pipeline — push'tan production'a

Bir Jenkinsfile Nasıl Görünür?

// Jenkinsfile — declarative pipeline
pipeline {
  agent any

  stages {
    stage('Build') {
      steps {
        sh './mvnw clean package -DskipTests'
      }
    }
    stage('Test') {
      steps {
        sh './mvnw test'
        junit 'target/surefire-reports/*.xml'
      }
    }
    stage('Docker Build & Push') {
      steps {
        sh 'docker build -t registry.local/app:${BUILD_NUMBER} .'
        sh 'docker push registry.local/app:${BUILD_NUMBER}'
      }
    }
    stage('Deploy to Staging') {
      when { branch 'develop' }
      steps {
        sh 'kubectl set image deployment/app app=registry.local/app:${BUILD_NUMBER}'
      }
    }
  }

  post {
    failure {
      slackSend(message: " Build #${BUILD_NUMBER} failed")
    }
  }
}

Diğer Araçlarla İlişkisi

  • Git (GitHub/GitLab): Tetikleyici. Jenkins webhook ile push'u dinler.
  • Docker / Container Registry: Build'in çıktısı genelde bir image olur, Jenkins onu registry'ye iter.
  • Argo CD: Modern setup'larda Jenkins sadece build/test/image-push'a kadar yapar, gerçek deploy işini Argo CD devralır. (GitOps deyince bu kasıt.)
  • SonarQube: Pipeline'da kod kalitesi kontrolü için sık eklenir.
  • Slack / Mail: Pipeline başarı/hata bildirimleri buralara düşer.
Stajyer notu
Jenkins'in modern alternatifleri: GitHub Actions, GitLab CI, CircleCI. Mantık aynı: "yaml/groovy ile pipeline yaz, push'ta tetiklensin". Birini öğren, hepsi tıkır tıkır gelir.
