BFF Mimarisi

BFF
Kısaca
Backend For Frontend — her client tipine (mobile, web, TV) özel bir ara katman. Downstream servisleri birleştirir, client'a uygun formatta cevap döner.
📖 BFF Pattern 📖 Microsoft Docs
Mobile → Gateway → BFF → Core → Fiba Bank akış şeması

Bu Ne? Neden Var?

BFF (Backend For Frontend), her client tipine — mobile, web tarayıcısı, akıllı TV — özel bir ara katmandır. Klasik API Gateway her şeye tek formatta cevap verirken, BFF mobil'in ihtiyacına göre özelleştirilmiş response döner. Örneğin web 50 field isteyebilir, mobil sadece 8'ine ihtiyaç duyar — BFF gereksiz veriyi mobil'e göndermez, batarya ve bant genişliği tasarrufu sağlar.

Şemada Mobile Client → Gateway → BFF → Core E → Fiba Bank zinciri var. Kullanıcı bir işlem başlattığında istek bu katmanları sırayla geçer. Her katmanın sorumluluğu birbirinden ayrı — separation of concerns.

Katmanlar Ne Yapar?

  • API Gateway: Şemadaki diamond (karar noktası). İsteğin kim olduğunu doğrular (auth), rate limit kontrol eder, hangi servise yönleneceğine karar verir. BFF'e ya da başka bir servise yönlendirir.
  • BFF: Asıl odak noktası. incoming isteği alır, Correlation ID ekler, header'ları zenginleştirir, gerekirse birden fazla downstream servisi paralel çağırır (aggregation), hepsini birleştirip outgoing response döner.
  • Core E: İş mantığının yaşadığı yer. Hesap bakiyesi, transfer logic, kural motoru buradadır. BFF'den temiz bir istek alır, temiz bir cevap döner.
  • Fiba Bank: En dipteki entegrasyon katmanı. Harici bir bankacılık sistemi ya da legacy core ile iletişim kurar. Core E bunu soyutlar — BFF'in haberi olmaz.

BFF'de Günlük Yazacağın Şeyler

// Spring Boot — tipik bir BFF endpoint'i
@RestController
@RequestMapping("/api/v1/accounts")
public class AccountBffController {

  @GetMapping("/{accountId}/summary")
  public ResponseEntity<AccountSummaryDto> getSummary(
      @PathVariable String accountId,
      @RequestHeader("X-Correlation-ID") String correlationId,
      @RequestParam(defaultValue = "tr") String lang) {

    // 1. Downstream servisleri PARALEL çağır
    CompletableFuture<AccountDto>  accountFuture  = coreClient.getAccount(accountId, correlationId);
    CompletableFuture<BalanceDto>  balanceFuture  = coreClient.getBalance(accountId, correlationId);
    CompletableFuture<List<TxDto>> txFuture       = coreClient.getLastTx(accountId, correlationId, 5);

    // 2. Hepsini bekle — parallelism burada devreye girer
    CompletableFuture.allOf(accountFuture, balanceFuture, txFuture).join();

    // 3. Mobil için sadece gerekli alanları döndür
    return ResponseEntity.ok(
      AccountSummaryDto.builder()
        .name(accountFuture.get().getOwnerName())
        .balance(balanceFuture.get().getAvailable())
        .lastTransactions(txFuture.get())
        .build()
    );
  }
}

Correlation ID — Nasıl Çalışır?

// Her isteğe otomatik Correlation ID ekleyen filter
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {

  private static final String HEADER = "X-Correlation-ID";

  @Override
  protected void doFilterInternal(HttpServletRequest req,
                                  HttpServletResponse res,
                                  FilterChain chain) throws IOException, ServletException {
    // Gelen header'da varsa al, yoksa yeni üret
    String correlationId = Optional
      .ofNullable(req.getHeader(HEADER))
      .orElse(UUID.randomUUID().toString());

    // MDC'ye koy → log'larda otomatik görünsün
    MDC.put("correlationId", correlationId);

    // Response header'ına da ekle → client takip edebilsin
    res.setHeader(HEADER, correlationId);

    try {
      chain.doFilter(req, res);
    } finally {
      MDC.clear();  // thread temizle — thread pool'da sızdırmasın
    }
  }
}

Artık log'larda her satırda [correlationId=abc-123] görünür. Bir hata olduğunda o ID'yi alıp tüm servis log'larında aratırsın — isteğin tüm yolculuğunu tek seferde görürsün. Buna distributed tracing denir.

Concurrency vs Parallelism — Pratik Fark

Concurrency (Eşzamanlılık)

  • Tek CPU core, birden fazla iş
  • İşler arasında hızlıca geçiş yapar (context switch)
  • Aynı anda görünür ama aslında sıralı
  • Örnek: Tek aşçı, 3 tencereyi sırayla karıştırır
  • Java: ExecutorService, Thread

Parallelism (Paralellik)

  • Birden fazla CPU core
  • İşler gerçekten aynı anda çalışır
  • Fiziksel olarak eş zamanlı
  • Örnek: 3 aşçı, 3 tencereyi aynı anda karıştırır
  • Java: CompletableFuture.allOf(), ForkJoinPool

BFF'de üç downstream servisi çağırırken paralel çağırırsın — biri 200ms, diğeri 150ms, öbürü 180ms sürüyorsa toplam süren 200ms olur, 530ms değil. Sıralı yapsaydın kullanıcı 530ms beklerdi.

⚡ Stajyer notu
BFF gördüğünde şunu anla: bu katman mobil'in sözcüsü. Core ne verirse versin, BFF onu mobil'e uygun hale getirir. Sen bu katmanda çalışacaksan her endpoint'te şu 3 soruyu sor: "Correlation ID var mı?", "Downstream çağrıları paralel mi?", "Mobil'e sadece lazım olan field'lar mı dönüyor?"
